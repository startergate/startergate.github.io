12:Tb31,<p>테스트?</p>
<ul>
<li>값이 원하는 형태가 되는가</li>
<li>원하는 동작을 연계해서 수행하는가</li>
<li>검증하고자 하는 메소드를 수행시켰을 때,<ul>
<li>원하는 값의 assert()가 true</li>
<li>원하는 동작의 verify()가 true</li>
</ul>
</li>
</ul>
<p>테스트를 어렵게 하는 것</p>
<ul>
<li>의존 class의 동작<ul>
<li>Mocking, Stub 활용</li>
</ul>
</li>
<li>안드로이드 의존 동작<ul>
<li>context 기능을 wrapping</li>
<li>=&gt; wrapping 클래스를 mocking</li>
</ul>
</li>
<li>=&gt; solve =&gt; testable architecture</li>
</ul>
<p>Architecture?</p>
<ul>
<li>코드의 역할을 분리하여 여러 이즘을 얻는다<ul>
<li>가독성 (높은 응집도)</li>
<li>변경 유연함 (낮은 결합도)</li>
</ul>
</li>
<li>MVP, MVVM</li>
<li>그냥 사용 시 Not Testable</li>
<li>몇 원칙을 기반으로 개선하면 Testable Architecture<ul>
<li>의존성 객체는 모두 주입<ul>
<li>static class를 일반 클래스로 변경</li>
</ul>
</li>
<li>안드로이드 의존 동작은 wrapping<ul>
<li>SDK =&gt; Context 기능 Wrapping</li>
<li>UI =&gt; View Interface로 Wrapping</li>
<li>DB / API =&gt; Repository Interface로 Wrapping</li>
<li>=&gt; MVP의 기본</li>
</ul>
</li>
<li>모든 동작은 Presenter를 사용<ul>
<li>View는 Presenter 실행만</li>
<li>Passive View</li>
</ul>
</li>
</ul>
</li>
</ul>
<p>Instrument Test</p>
<ul>
<li>UI Test</li>
<li>DB Test</li>
</ul>
<p>Testable Architecture라면 View와 Repository만 추가적으로 테스트</p>
<p>테스트를 어렵게 하는게 저거 2개?<br />
=&gt; x. QA로 하는게 나은거 같다<br />
테스트를 추가할 시간이 없다<br />
효용성을 모르겠다. 너무 바빠서 동기가 안 산다</p>
<p>테스트의 효용성</p>
<ul>
<li>동작 확인</li>
<li>변경 유연성 확보<ul>
<li>테스트가 있는 class는 변경해도 안심</li>
<li>장기적으로 테스트가 있는게 생산성이 훨씬 빠름</li>
</ul>
</li>
<li>코드리뷰를 도움<ul>
<li>테스트는 의도를 명시화</li>
<li>테스트를 파악하고 코드를 보면 리뷰가 수월하다</li>
</ul>
</li>
</ul>
<p>테스트 동기부여</p>
<ul>
<li>리포트로 현타를 받자<ul>
<li>Codecov</li>
</ul>
</li>
<li>익숙해질때까지 강제성을 두자<ul>
<li>커버리지 이전보다 안 높으면 &quot;Don&#39;t Approve&quot;</li>
</ul>
</li>
<li>쉬운 것부터 차근차근<ul>
<li>Presenter/Unit 테스트가<ul>
<li>속도가 빠르다</li>
<li>수명도 길다</li>
</ul>
</li>
</ul>
</li>
</ul>
<p>결론</p>
<ul>
<li>테스트를 잘 하려면 역할이 잘 분리된 Architecture가 필요</li>
<li>실제 서비스에서는 영향을 주고받는 컨텍스트가 많음<ul>
<li>QA는 여전히 필요함</li>
</ul>
</li>
<li>복잡하지 않은 동작은 테스트로 검증!</li>
</ul>
