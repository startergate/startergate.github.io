<h3>Kafka</h3>
<ul>
<li><p>Topic</p>
<ul>
<li>1개 이상의 Partition으로 분할, 1개 이상의 Replica로 복제된 Log 자료 구조</li>
</ul>
</li>
<li><p>Client</p>
<ul>
<li>Producer: 쓰고자 하는 Topic Partition의 맨 끝에 record를 추가</li>
<li>Consumer: 읽어오고자 하는 Topic의 Partition에 저장된 record를 순차적으로 읽어옴</li>
</ul>
</li>
<li><p>Consumer Group</p>
<ul>
<li>같은 group.id 설정 값을 가진 Consumer들은 하나의 Consumer Group을 이룬다</li>
<li>같은 Consumer Group에 속한 Consumer들이 Topic에 속한 Partition들을 나눠서 읽는다</li>
<li>Consumer Group == &quot;논리적인 Comsumer&quot;</li>
<li>거대한 Consumer 하나가 전체 Topic 내용을 읽어들이는 것 처럼 보인다</li>
<li>제대로 동작하기 위해 필요한 것은?<ul>
<li>중복도 누락도 없이 할당해주는 매커니즘 (Partition Assignment)</li>
<li>어디서부터 작업을 시작하면 되는지 저장하고 불러오는 매커니즘 (Offset Commit)</li>
</ul>
</li>
</ul>
</li>
<li><p>Consumer Coordination</p>
<ul>
<li>Comsumer Group Coordinator<ul>
<li>Consumer Group에 변경이 생겼는지 탐지</li>
<li>TopicPartition에 변경이 생겼는지 탐지</li>
<li>Comsumer Group Leader와 나머지 Comsumer들간의 Communication 중개</li>
</ul>
</li>
<li>Consumer Group Leader<ul>
<li>현재 구독중인 topic의 파티션들을 consumer들에 할당</li>
</ul>
</li>
<li>Broker를 재시작할 필요 없이 더 유연하고 확장 가능한 파티션 할당을 지원하기 위해</li>
</ul>
</li>
</ul>
<h3>Cloud 환경에서의 Consumer Group Coordination</h3>
<ul>
<li>group.instance.id<ul>
<li>정적 그룹 멤버십</li>
<li>정상적 재시작 이전에 할당되어 있던 파티션들을 다시 할당</li>
<li>단순 pod 재시작 때문에 Partition Rebalance가 발생하는 사태를 방지</li>
</ul>
</li>
<li>session.timeout.ms<ul>
<li>Consumer 프로세스가 Broker가 신호를 주고받지 않고도 리밸런스를 생성시키지 않는 최소 시간</li>
</ul>
</li>
<li>broker.rack<ul>
<li>Failover Replica로부터 읽기</li>
<li>클라우드 시대로 넘어오면서 의미 변화<ul>
<li>물리적 서버 랙 -&gt; 가용 영역</li>
<li>Consumer와 Leader Replica가 서로 다른 가용 영역에 있으면?<ul>
<li>Consumer가 위치한 AZ를 알고 있고, 해당 AZ에 leader replica와 동기화된 상태를 유지고하 있는 follower replica가 있으면 거기서 가져오자</li>
</ul>
</li>
</ul>
</li>
</ul>
</li>
</ul>
<h3>네이버 스케일</h3>
<ul>
<li>본질적인 원인<ul>
<li>Rack이 가리키는 바가 지나치게 애매모호 하다</li>
<li>Partition Assigner가 rack 정보를 고려하지 않는다</li>
</ul>
</li>
