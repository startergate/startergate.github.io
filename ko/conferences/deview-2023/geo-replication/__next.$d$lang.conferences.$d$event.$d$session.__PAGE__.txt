<h2 id="message-queue-in-geo-replication">Message Queue in Geo-Replication</h2>
<h3>Key Elements</h3>
<ul>
<li>Out-of-the-box feature<ul>
<li>개발 난이도와 관리 측면에서 중요</li>
</ul>
</li>
<li>Synchronous &amp; Asynchronous Replication<ul>
<li>Synchronous Replication은 데이터 정합정에 강점</li>
<li>Asynchronous Replication은 Dynamic Scalability wjrdyd rksmd</li>
</ul>
</li>

<li>Asynchronous Replication 의 Replication Lag 측정</li>

</ul>
</li>
</ul>
<h3>Kafka Stretch Cluster</h3>
<ul>
<li>Synchronous Replication on Kafka</li>
<li>IDC 간 Network Latency 발생</li>
</ul>
<h3>Kafka MirrorMaker</h3>
<ul>
<li>Asynchronous Replication on Kafka</li>
<li>Active–Active 구성 시, 동일 토픽 간 Multi-named Topic Consuming 필요</li>
</ul>
<h3>Pulsar Geo Replication</h3>
<ul>
<li>Synchronous Replication<ul>
<li>Region Aware Placement Policy</li>
<li>Multi-Cluster + 단일 Zookeeper ensemble</li>
<li>Multi IDC Data Write Ack</li>
</ul>
</li>
<li>Asynchronous Replication<ul>
<li>Rack Aware Placement Policy</li>
<li>Write Ack 없이 동작</li>
<li>복제 지연 발생 가능</li>
</ul>
</li>
<li>Pulsar Automatic Cluster Failover API<ul>
<li>Primary Cluster의 장애 탐지 시 Secondary Cluster로 자동 전환</li>
</ul>
</li>
</ul>

</ul>

</ul>

<li>Data Enrichment 결과 데이터를 얼마나 효과적으로 재사용할 수 있는가?</li>
<li>장애 복구 시 효과적인 리소스 사용</li>
</ul>
</li>
</ul>
<h2 id="cloud-friendliness-in-geo-replication">Cloud Friendliness in Geo Replication</h2>
<p>비용 효율적인 Geo Replication 을 위해서는 클라우드 친화 플랫폼이 필요</p>
<h3>Key Elements</h3>
<ul>
<li>HPA 기반의 Dynamic Resource 할당<ul>
<li>HPA를 기반으로 한 탄력적 Resource Scaling 을 통해서 빠르게 장애 대응</li>
<li>Active/Active, Active/Standby 와 같은 다양한 Resource 구성에 효과적으로 대응</li>
<li>Cost Efficient Geo Replication을 위한 필수적 특징</li>
</ul>
</li>
<li>Modularly Designed Sub-system<ul>
<li>Monolithic Design 의 경우 Resource 를 효과적으로 Scaling 하기에 불리한 구조</li>
<li>Micro Service Architecture 에 유리한 Modular design</li>
</ul>
</li>
<li>스케일 인/아웃으로 인한 제약 없음<ul>
<li>Resource Scaling 으로 성능 저하/기능 제약이 있는 경우 Cloud의 Resource 환경에 부적합</li>
</ul>
</li>
</ul>
